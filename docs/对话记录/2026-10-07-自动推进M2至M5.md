## 1. 自主推进的决策依据

用户不在场，因此第一步不是写代码，而是判断"哪些事可以自主做、哪些必须等用户"。

**判断标准**：

| 类别 | 例子 | 处理 |
|---|---|---|
| 不依赖麦克风、且需求文档已明确 | TAB 谱面、会话模式、SM-2、统计页 | ✅ 自主实现 |
| 不依赖麦克风、但需求文档留了【待确认】 | 具体配色、默认时长 | ⚠️ 按文档默认值实现，留出设置项 |
| 依赖麦克风 | 调音器实机准确度、低音弦判定效果 | ⛔ 不做，等用户 |
| 需要用户审美判断 | 界面是否好看、手感 | ⛔ 不替用户决定，留给验收 |
| 流程性动作 | 打里程碑标签 | ⛔ **不做**（PRD §16.4 规定验收通过后才打） |

这条判断的关键是最后两行：**能做的尽量做，需要用户拍板的一律不替用户决定**。
因此本段期间没有打任何里程碑标签。

## 2. 逐里程碑记录

### 2.1 M2 模块一「看谱找音」

**自主决定**

- 练习模块做成"协议 + 注册表"：新增练习 = 新增一个包 + 一行注册，
  首页卡片自动生成，主程序零改动。理由是需求明确要求"可不断扩展"。
- 出题、渲染、判定配置三者分离：模块只描述"出什么题、怎么画、判定参数"，
  会话控制器只管流程。这样做的好处是**全部逻辑都能用合成事件测试**。
- 判定沿用 M1 的 `PitchClassJudge`，不另起一套。

**发现并修复的缺陷**

1. **残留音把下一题秒判错**（严重）——用户答对后琴弦还在响，残留帧被喂给下一题；
   连续两题音名相同时，残留音正好"符合"上一题的答案，于是把新题判错。
   吉他音可响数秒、比默认宽容期（2 秒）还长，因此这是**真实使用中必然发生**的问题。
   修复：判定器引入"武装"机制（新拨弦 / 不同音名 / 静音 300ms 才恢复判定）。
2. 练习屏相对导入层级写错（`..core` 应为 `...core`）——由打包自检的界面冒烟抓出。

### 2.2 M3 学习机制

**自主决定**

- 简化 SM-2（间隔 0/1/3/7/16/35/75/160 天），而不是完整 SM-2 的 ease 因子调整。
  理由：需求文档给的就是固定间隔序列。
- 调度器**不依赖数据库、不依赖 Qt**，随机种子与时钟可注入——这样才能把
  "出题序列"当作可测对象。
- 训练项键沿用 M2 已确定的 `音名 × 把位区间`。

**发现并修复的缺陷**（都只有把调度器跑成序列才能发现）

1. 同一个音连出 4 题；
2. **回炉机制形同虚设**：失败的题同时是"当天到期项"，在回炉到点前被普通通道抽走。
   修复时第一版修错了（把"回炉锁"与"防连出"合成一个可回退的过滤器），
   导致单候选场景下回炉锁被绕过——**两者必须区分：回炉锁不可回退，防连出可回退**；
3. 全部题目都在等回炉时死锁（连续全错 → 候选为空）。

**额外做的验证**

用户无法实机验证"记忆曲线到底有没有用"，所以补了跨天端到端测试：
今天练过的音，第二天全部到期、同一天不重复轰炸、连续几天间隔按 1→3→7 增长。

### 2.3 M4 统计报告

**自主决定**

- 图表**自绘**而不是用 QtCharts。理由：打包时已排除 QtCharts（体积考虑），
  自绘三个控件更轻，外观也更统一。
- 统计查询取原始行、在 Python 里按本地日期分桶，而不是在 SQLite 里做时区转换。

**发现并修复的缺陷**

- **时间戳口径不一致**：`attempts.answered_at` 存的是"本地裸时间"，
  而 sessions/items 存 UTC。后果是下午 8 点之后的练习会被算到前一天，
  逐日曲线与时段对比全部错位，单机使用时极难发现。

### 2.4 M5 打磨与交付

范围不是自己定的，而是回查需求文档后确认的：**FR-1000 数据与备份**
（自动备份、档案 JSON 导入导出）此前只做了数据库层，界面与档案层还没做；
另有 §10 验收标准里可自动化验证的条目。

**发现并修复的缺陷**（前两个是阻断级）

1. **音频线程根本构造不出来**：`AnalyzerThread` 是 dataclass 修饰的 Thread 子类，
   生成的 `__eq__` 使其不可哈希，而 Thread 要把自己放进 WeakSet →
   `AudioSession.start()` 一构造就崩。**插上麦克风一启动就崩，而测试全绿**
   （原测试直接用 FrameAnalyzer，从不构造后台线程）。
2. dataclass 字段 `_stop` 遮蔽 `Thread._stop()`：修好构造后 `join()` 又崩。
3. **备份在 WAL 模式下会丢数据**：原用文件拷贝，未 checkpoint 的事务还在 `-wal` 里，
   而"刚练完就备份"恰恰最需要这些数据。改用 SQLite 在线备份 API。

**顺带发现**：`SessionStats.reaction_times` 无界增长，违反 NFR-06 —— 改为累加式。

**关于性能测量的一处自我纠正**：第一版基准打印出"内存 0.0 MB → 0.0 MB，结论通过"。
这是测量函数静默失败（Windows 伪句柄被截断成 32 位）导致的**假通过**。
已修正测量，并让脚本在测不到内存时如实报"测量无效"而不是判通过。
随后 4 小时模拟显示常驻内存线性增长 16%，又用 `tracemalloc` 复核，
确认**没有 Python 层泄漏**（909 题仅 +4.7 KB、存活对象 +253），
RSS 增长来自压缩模拟的分配器碎片。基准现在同时给出两个判据并注明局限。

## 3. 流程上的偏差与处理

| 偏差 | 原因 | 处理 |
|---|---|---|
| 没有向用户提问 | 用户不在场（关机） | 需要拍板的事项一律延后，不替用户决定；按需求文档默认值实现并保留设置项 |

| 一次自动轮次跨越整个里程碑 | 用户不在场且目标要求持续推进 | 每个里程碑单独提交并在开发记录中说明验证情况 |

4. **默认值确认**：默认难度 L1、默认 30 题、默认 15 分钟是否符合使用习惯。
