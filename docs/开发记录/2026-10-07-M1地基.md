## 1. 本机环境的三个硬约束（实测确认）

M1 最耗时的部分不是写功能，而是查清本机环境的三个"陷阱"并做成兼容层。

### 1.1 `os.mkdir(path, 0o700)` 创建的目录不可写

| 创建方式 | 结果 |
|---|---|
| `os.mkdir(path, 0o700)` | ❌ ACL 损坏，**连 `icacls` 都无法处理**，读写全部被拒 |
| `tempfile.mkdtemp()`（内部用 0o700） | ❌ 同上 |
| `os.mkdir(path, 0o755)` / `0o777` | ✅ 正常 |

**影响**：pip 无法安装任何包（内部用 mkdtemp 解包）；pytest 的 basetemp / 编号临时
目录机制会让整个测试会话在清理阶段崩溃。

**对策**：
- 依赖改为**解包官方 wheel 到 `.vendor/`**（`run.py` / `conftest.py` 负责加入 `sys.path`）；
- `src/jitatrainer/compat.py` 运行期探测并修补 `tempfile.mkdtemp`；
- `conftest.py` **接管 pytest 的 `tmp_path` 夹具**，把临时目录固定到工作区内的
  `.tmp/tests/`，完全绕开 pytest 的临时目录回收逻辑。

### 1.2 pip 的失败链条（供日后排查）

```
pip install sounddevice
  → normal site-packages is not writeable（沙箱只允许写工作区）
  → Defaulting to user installation
  → mkdtemp 解包 → PermissionError: ...whl.metadata
```

### 1.3 PowerShell 的 schannel TLS 不可用

`curl` / `Invoke-RestMethod` 访问 GitHub 报
`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`，
而 Python 自带 OpenSSL 正常、git 正常。因此所有 HTTP 调用统一走 Python。

> 遗留：`.tmp/pytest` 与 `.tmp/pytest-work` 两个目录在首次崩溃时被写坏，
> `takeown` / `icacls` / `Remove-Item` 均无法清除，只能留在本地
> （已被 `.gitignore` 排除，不影响仓库与运行）。

## 2. 交付内容

### 2.1 代码结构

```
src/jitatrainer/
├─ app.py                    入口 + 离屏自检（含真实麦克风探测）
├─ compat.py                 环境兼容层
├─ paths.py                  绿色版路径解析
├─ core/theory/              notes / tuning / levels / fretboard
├─ core/audio/               pitch_yin / ring / gate / analyzer / capture / session / device / events
├─ core/judge/               base / pitch_class_judge
├─ data/                     db / settings / migrations
├─ ui/                       main_window / theme / audio_bridge
│  ├─ pages/                 home / tuner / wizard
│  └─ widgets/               pitch_meter
└─ i18n/                     zh_CN.json / en_US.json
```

### 2.2 音频链路（M1 的核心）

```
麦克风 → sounddevice 回调（只做一次拷贝）
       → 环形缓冲（0.5s，单生产者单消费者）
       → 分析线程（每 10ms 取 2048 帧）
       → 门限（低于门限直接跳过 YIN，省 CPU）
       → 起音检测（相对最近 3 帧最大值的跳变）
       → YIN + 保守谐波校验（置信度 <0.80 直接拒绝）
       → PitchEvent → 事件队列 → UI 定时器轮询
```

关键设计：`FrameAnalyzer.process(frame, t)` 是**纯函数式**的，线程与算法分离，
因此整条链路可以在没有麦克风的情况下用合成音频完整测试。

### 2.3 判定引擎

滑动窗口 + 多数表决；三档稳定时长预设（150/200/300ms，默认平衡）；
三种试音模式（宽容期/严格/宽容）；单帧置信度下限 0.80；容差默认 ±25 音分。

### 2.4 界面

- 首页：档案信息、设备与门限、稳定时长档位、模块入口卡片
- 调音器：`PitchMeter` 指针式音分表 + 自动识别当前弦
- 首次运行向导：选设备 → 测环境噪声（3s，分位数估计）→ 试弹校准六根弦
- 中英双语切换

## 5. 真实吉他实测（2026-10-07，M1 的最后一环）

用户在场、用吉他依次拨响六根空弦，程序实录 30 秒（设备：**Realtek 内置麦克风阵列
@48kHz**——本机没有任何 USB 麦克风，蓝牙耳机麦克风全部处于 −96~−127dB 的静音状态）。

### 5.1 实测暴露的两个问题

**问题一：琴本身没调准（不是程序的问题）**

| 弦 | 标准音 | 实测 | 偏差 |
|---|---|---|---|
| 第 6 弦 | E2 82.41 | ≈78.1 Hz | −93 音分 |
| 第 5 弦 | A2 110.00 | ≈106.2 Hz | −61 音分 |
| 第 4 弦 | D3 146.83 | ≈139.8 Hz | −85 音分 |
| 第 3 弦 | G3 196.00 | ≈194.1 Hz | −16 音分 |
| 第 2 弦 | B3 246.94 | ≈237.2 Hz | −70 音分 |
| 第 1 弦 | E4 329.63 | ≈323.4 Hz | −33 音分 |

六根弦整体偏低 16–93 音分。**这正是向导里"试弹校准"要求先调准琴的原因。**

**问题二：程序确实有一个缺陷 —— 低音弦高八度锁定**

频谱分析给出决定性证据（第 6 弦）：

```
基频区 70–90Hz   ：峰值 76.2 Hz   幅度 34
二次谐波 145–170Hz：峰值 155.3 Hz  幅度 626     ← 基频只有它的 1/18
```

内置麦克风对 60–150Hz 响应很差，把基频压到二次谐波的 1/18，YIN 的"首个低于阈值
的谷"规则于是锁到了高八度，报告 `D#3 / 155.5Hz` 而不是 `D#2 / 78Hz`。

而原来的谐波校验**刻意跳过了 200Hz 以下的全部候选**（那是为了避免第一版激进规则
在短窗口下误伤正确基频），结果就是：**低频区的高八度锁定完全没人管**。
这是技术方案风险表里承诺要缓解、却实际没有兑现的一项，只有真实录音能发现。

### 5.2 修复

在 `harmonic_correct` 中把两类方向相反的误判分开处理：

| 频段 | 误判方向 | 判据 |
|---|---|---|
| 低频区（≤420Hz） | 高八度锁定 | f0/2 仍在吉他音域内（≥60Hz）、且频谱中 f0/2 处**存在**局部峰（幅度 > f0 的 2%，且 > 60–1200Hz 频带中位幅度的 3 倍）→ 向下修正一个八度 |
| 高频区（>420Hz） | 把二次谐波当基频 | 保持原有的**保守**规则：要求 f0 与 f0/2 至少相隔 4 个频点，且 f0/2 处谱峰强于 f0 的 1.2 倍 |

另外把谐波校验用的 FFT 长度改为窗口的 4 倍补零，谱峰定位精度大幅提高。

修复后同一段录音：

```
修复前：D#3 155.5Hz    修复后：D#2 78.10Hz   ✅
```

### 5.3 第二次实录：发现"十二度锁定"

第一次修复后重新实录（60 秒，峰值 −9.4 dBFS，麦克风仍为内置阵列），逐弦频谱核对：

| 弦 | 真实基频 | 最强谱峰 | 识别结果 | 判定 |
|---|---|---|---|---|
| 第 6 弦 | 78.1 Hz | 155.3 Hz（基频的 1/18） | D#2 78.09 | ✅ 修复生效 |
| **第 5 弦** | **106.9 Hz** | **317.9 Hz（基频的 1/19）** | **D#4 318** ❌ | **十二度锁定** |
| 第 4 弦 | 139.2 Hz | 139.2 Hz（基频最强） | C#3 139.91 | ✅ |
| 第 3 弦 | 189.0 Hz | 189.0 Hz | F#3 188.74 | ✅ |
| 第 2 弦 | 237.3 Hz | 237.3 Hz | A#3 237.13 | ✅ |
| 第 1 弦 | 322.3 Hz | 322.3 Hz | E4 322.48 | ✅ |

第 5 弦的基频只有三次谐波的 **1/19**，YIN 锁到了十二度（3 倍频）。
上一轮只修了"÷ 2 八度"这一种锁定，÷3 无人处理。

**修复**：把向下搜索从"只查 hz/2"推广到"查 hz/2 与 hz/3"，并新增一条判据 ——
**候选基频的二次谐波处也必须有谱支持**。这一条用于区分"真正的低音"与
"随手把高音拉低"：真实低音一定在 f0 和 2f0 处同时有能量，而普通高音不会。
多个候选都成立时取最低的那个。

修复后同一段录音：第 5 弦输出 **G#2 106.34Hz**（A2 −59 音分），六根弦全部落在正确音区。

### 5.4 固件与回归测试

把两次实录中的关键片段都切段后作为**回归固件**纳入仓库：

| 固件 | 内容 | 复现的问题 |
|---|---|---|
| `tests/fixtures/real_open_strings.wav` | 第一次实录的六根弦（6 段 × 0.5s） | 第 6 弦八度锁定 |
| `tests/fixtures/real_twelfth_lock.wav` | 第二次实录的第 5 弦片段（0.8s） | 十二度锁定 |

`tests/test_real_recording.py` 的断言是"每根弦必须落在正确音区（±1.5 个半音）"——
八度误判偏约 12 个半音、十二度误判偏约 19 个半音，都会必然失败。
另有单元测试直接验证弱基频场景的向下修正、以及"没有低八度成分时不得乱改"。

> 两个编写测试时踩到的坑：
> 1. 按"段首 + 固定偏移"取样会漏掉第 3、1 弦（这两次拨弦只维持 0.10–0.11 秒
>    就衰减到门限以下），改为**段内扫描能量最强窗口**后通过；
> 2. 合成测试音的基频比例一开始取 2%，恰好卡在判据阈值上（6.88 vs 6.94）。
>    改为**直接使用实测比例**（八度案例 1/18、十二度案例 1/19），
>    避免把阈值卡在临界点上。

### 5.5 结论：琴需要调音

两次实录都显示六根弦整体偏低 **38–93 音分**（不是程序的问题）：

| 弦 | 标准音 | 目标频率 | 实测 | 偏差 |
|---|---|---|---|---|
| 第 6 弦 | E2 | 82.41 Hz | 78.1 Hz | −93 音分 |
| 第 5 弦 | A2 | 110.00 Hz | 106.3 Hz | −61 音分 |
| 第 4 弦 | D3 | 146.83 Hz | 139.9 Hz | −85 音分 |
| 第 3 弦 | G3 | 196.00 Hz | 188.7 Hz | −65 音分 |
| 第 2 弦 | B3 | 246.94 Hz | 237.1 Hz | −70 音分 |

**这正是向导要求"先调准琴再试弹校准"的原因**：琴不准时，校准会把琴的偏差

### 5.6 第三次尝试：设备层面卡住了

用户把音频改为"只用一个 USB 声卡工作"后重测，但设备探测显示
**该 USB 声卡没有向 Windows 暴露可用的录音端点**：

| 状态 | 设备 |
|---|---|
| ✅ 能打开 | `[0] MME 声音映射器`、`[1] MME Beosound A1`、`[7][8] DirectSound`、`[18] WASAPI Beosound A1` |
| ❌ 所有参数组合都打不开 | SteelSeries Sonar（虚拟声卡）、Realtek 内置阵列、各蓝牙免提设备（WDM-KS 独占模式） |

其中 `[0]` 映射器与 `[1] Beosound A1` 读数完全一致，说明**当时的 Windows 默认录音设备
是蓝牙音箱 Beosound A1**，而不是 USB 声卡。

用映射器录了 150 秒，时间轴诊断结果：

```
整体峰值        -12.8 dBFS
有信号的秒数     9 / 150
数字静音的秒数   94 / 150
```

即：**这个设备几乎不可用**。蓝牙麦克风在"有声音时才开闸"（典型 VAD 行为），
加上音箱离吉他太远，150 秒里只留下 9 秒碎片，无法支撑练习判定。

**结论**：这不是程序的问题，而是设备不可用。为此新增自检工具
`tools/mic_check.py`（实时电平条 + 可用性判定），以后可以先验证设备再录音，
不必反复盲测。

### 5.7 顺带修掉的一个真 bug：采样率写死

分析工具 `tools/capture_fixture.py` 把采样率写死为 48000，而这次录音是 **44100Hz**。
如果直接分析，所有频率会被整体放大 48000/44100 = 1.088 倍，也就是**结果普遍偏高约 147 音分**——
一个"静默给出错误答案"的典型缺陷。

已改为从 WAV 文件头读取采样率，并按实际采样率构造检测器。
（程序本体没有这个问题：`AudioSession` 从设置读取采样率，向导会用
`negotiate_samplerate()` 把设备实际支持的采样率写回设置。）

### 5.8 用户自己录制的两个样本：把问题彻底定位

用户用 Windows 自带录音机录了两段（48kHz 立体声 AAC，峰值 −4.5/−4.6 dBFS，
质量明显好于我自动录的样本），弹奏顺序 **6 → 5 → 4 → 3 → 2 → 1**，每弦 3 下。

**逐弦结果**：

| 弦 | 录音1 | 录音2 | 该弦时段峰值 |
|---|---|---|---|
| 第 6 弦 E2 | ❌ 未识别到 | ❌ 锁到二次谐波（D#3） | 录音1 −42~−69 dB |
| 第 5 弦 A2 | ❌ 未识别到 | ✅ 106.66Hz（−53 音分） | 录音1 −52~−69 dB |
| 第 4 弦 D3 | ✅ 140.50Hz（−76 音分） | ✅ 140.53Hz（−76 音分） | −15~−22 dB |
| 第 3 弦 G3 | ✅ 189.12Hz（−62 音分） | ✅ 189.22Hz（−61 音分） | −20~−38 dB |
| 第 2 弦 B3 | ✅ 237.57Hz（−67 音分） | ✅ 237.54Hz（−67 音分） | −13~−48 dB |
| 第 1 弦 E4 | ✅ 322.28Hz（−39 音分） | ✅ 322.53Hz（−38 音分） | −12~−33 dB |

**结论一：用户的主观观察是对的，但弦序号需要对齐。**
用户说"第 1、2 弦录不好，其他弦正常"——按他"依次拨 1-6 弦"的弹奏顺序，
他的"1 弦"指的就是**最粗的那根（低音 E）**。所以问题弦是**最低的两根弦（E2、A2）**，
与物理预期完全一致：**低音弦电平比高音弦低约 30 dB**。

**结论二：根因是麦克风低频响应，且可以用更长的分析窗口部分缓解。**

同一段录音（录音2 第 6 弦）在不同窗口下：

| 分析窗口 | 中位频率 | 识别 | 落在 E2 音区 |
|---|---|---|---|
| 2048（43ms） | 157.0 Hz | D#3 ❌ | 12/36（33%） |
| 4096（85ms） | 157.2 Hz | D#3 ❌ | — |
| **8192（171ms）** | **79.2 Hz** | **D#2 ✅** | 24/47（51%） |
| 16384（341ms） | 78.7 Hz | D#2 ✅ | — |

**实现**：`FrameAnalyzer` 增加**低频增强**路径——快路径（2048 帧）结果落在
220Hz 以下时，用 8192 帧长窗口复核一次，只接受把频率向真实基频拉回的结果。
中高音区的延迟完全不变；低音区多 128ms。

**诚实的局限**：即使增强后也只有约 55% 的帧能锁定真实基频。所以
- 判定层不受影响（多数表决 + 音名判定，E2 与 E3 音名相同，**锁到八度不会判错**）；
- 调音器页增加**显示平滑**（最近 24 帧众数），避免指针在 D#2/D#3 之间跳动。

**结论三：两次独立录音都显示琴整体偏低 38~76 音分**，与之前两次实录一致——
琴确实需要调音。

### 5.9 关于测试流程的教训

我之前的做法是"我启动录音 → 发消息告诉用户开始弹"，但消息要等这一轮结束才显示，
**用户根本不知道什么时候开始录**。这是测试设计问题，不是用户的问题。

改进后的流程（已验证有效）：**用户用 Windows 自带录音机自己录，把文件放到
`用户提供资料/` 目录，我来分析**。这样既没有时机问题，录音质量也更好
（用户录的峰值 −4.5dBFS，我自动录的 −9.4dBFS）。
