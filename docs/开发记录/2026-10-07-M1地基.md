## 1. 本机环境的三个硬约束（实测确认）

M1 最耗时的部分不是写功能，而是查清本机环境的三个"陷阱"并做成兼容层。

### 1.1 `os.mkdir(path, 0o700)` 创建的目录不可写

| 创建方式 | 结果 |
|---|---|
| `os.mkdir(path, 0o700)` | ❌ ACL 损坏，**连 `icacls` 都无法处理**，读写全部被拒 |
| `tempfile.mkdtemp()`（内部用 0o700） | ❌ 同上 |
| `os.mkdir(path, 0o755)` / `0o777` | ✅ 正常 |

**影响**：pip 无法安装任何包（内部用 mkdtemp 解包）；pytest 的 basetemp / 编号临时
目录机制会让整个测试会话在清理阶段崩溃。

**对策**：
- 依赖改为**解包官方 wheel 到 `.vendor/`**（`run.py` / `conftest.py` 负责加入 `sys.path`）；
- `src/jitatrainer/compat.py` 运行期探测并修补 `tempfile.mkdtemp`；
- `conftest.py` **接管 pytest 的 `tmp_path` 夹具**，把临时目录固定到工作区内的
  `.tmp/tests/`，完全绕开 pytest 的临时目录回收逻辑。

### 1.2 pip 的失败链条（供日后排查）

```
pip install sounddevice
  → normal site-packages is not writeable（沙箱只允许写工作区）
  → Defaulting to user installation
  → mkdtemp 解包 → PermissionError: ...whl.metadata
```

### 1.3 PowerShell 的 schannel TLS 不可用

`curl` / `Invoke-RestMethod` 访问 GitHub 报
`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`，
而 Python 自带 OpenSSL 正常、git 正常。因此所有 HTTP 调用统一走 Python。

> 遗留：`.tmp/pytest` 与 `.tmp/pytest-work` 两个目录在首次崩溃时被写坏，
> `takeown` / `icacls` / `Remove-Item` 均无法清除，只能留在本地
> （已被 `.gitignore` 排除，不影响仓库与运行）。

## 2. 交付内容

### 2.1 代码结构

```
src/jitatrainer/
├─ app.py                    入口 + 离屏自检（含真实麦克风探测）
├─ compat.py                 环境兼容层
├─ paths.py                  绿色版路径解析
├─ core/theory/              notes / tuning / levels / fretboard
├─ core/audio/               pitch_yin / ring / gate / analyzer / capture / session / device / events
├─ core/judge/               base / pitch_class_judge
├─ data/                     db / settings / migrations
├─ ui/                       main_window / theme / audio_bridge
│  ├─ pages/                 home / tuner / wizard
│  └─ widgets/               pitch_meter
└─ i18n/                     zh_CN.json / en_US.json
```

### 2.2 音频链路（M1 的核心）

```
麦克风 → sounddevice 回调（只做一次拷贝）
       → 环形缓冲（0.5s，单生产者单消费者）
       → 分析线程（每 10ms 取 2048 帧）
       → 门限（低于门限直接跳过 YIN，省 CPU）
       → 起音检测（相对最近 3 帧最大值的跳变）
       → YIN + 保守谐波校验（置信度 <0.80 直接拒绝）
       → PitchEvent → 事件队列 → UI 定时器轮询
```

关键设计：`FrameAnalyzer.process(frame, t)` 是**纯函数式**的，线程与算法分离，
因此整条链路可以在没有麦克风的情况下用合成音频完整测试。

### 2.3 判定引擎

滑动窗口 + 多数表决；三档稳定时长预设（150/200/300ms，默认平衡）；
三种试音模式（宽容期/严格/宽容）；单帧置信度下限 0.80；容差默认 ±25 音分。

### 2.4 界面

- 首页：档案信息、设备与门限、稳定时长档位、模块入口卡片
- 调音器：`PitchMeter` 指针式音分表 + 自动识别当前弦
- 首次运行向导：选设备 → 测环境噪声（3s，分位数估计）→ 试弹校准六根弦
- 中英双语切换

## 3. 测试抓出的 bug（都会造成实际故障）

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | **`settings.get_int("samplerate")` 返回 0** —— 类型化 getter 把数字默认值当成字符串默认值，覆盖了 DEFAULTS | 采集时请求 0Hz 采样率，录音直接失败 | 重构 `get()` 语义：`default=None` 表示走 DEFAULTS；类型化 getter 不再传 default |
| 2 | `PitchResult` 低置信度结果仍被标记为"有效" | 实测 10dB 噪声把 B3 读成 E（置信度 0.49）——**冤判** | 新增 `accepted` 字段，`valid` 同时要求 accepted |
| 3 | 起音检测用均值作基线，且静音帧根本不进历史 | 起音永远检测不到（基线建不起来） | 改为相对**最近 3 帧最大值**的跳变，静音帧同样参与历史 |
| 4 | `PitchEvent` 缺 `pitch_class` 属性 | 判定层整片测试报错 | 补齐派生属性 |
| 5 | 备份文件名只精确到秒 | 同一秒内两次备份互相覆盖，**静默丢备份** | 毫秒 + 序号兜底 |
| 6 | `QPushButton.alignment()` 不存在 | 主窗口一构造就崩溃（自检退出码 4） | 去掉该参数 |
| 7 | `capture_fixture.py` 把频率当 MIDI 号传给 `midi_name` | 82.87Hz 显示成 B5 | 先 `hz_to_midi` 再取名 |

第 1、2 条尤其关键：一个是"静默返回错误配置"，一个是"静默给出错误音名"，
都属于不报错但结果错的类型，只有测试能发现。

## 5. 真实吉他实测（2026-10-07，M1 的最后一环）

用户在场、用吉他依次拨响六根空弦，程序实录 30 秒（设备：**Realtek 内置麦克风阵列
@48kHz**——本机没有任何 USB 麦克风，蓝牙耳机麦克风全部处于 −96~−127dB 的静音状态）。

### 5.1 实测暴露的两个问题

**问题一：琴本身没调准（不是程序的问题）**

| 弦 | 标准音 | 实测 | 偏差 |
|---|---|---|---|
| 第 6 弦 | E2 82.41 | ≈78.1 Hz | −93 音分 |
| 第 5 弦 | A2 110.00 | ≈106.2 Hz | −61 音分 |
| 第 4 弦 | D3 146.83 | ≈139.8 Hz | −85 音分 |
| 第 3 弦 | G3 196.00 | ≈194.1 Hz | −16 音分 |
| 第 2 弦 | B3 246.94 | ≈237.2 Hz | −70 音分 |
| 第 1 弦 | E4 329.63 | ≈323.4 Hz | −33 音分 |

六根弦整体偏低 16–93 音分。**这正是向导里"试弹校准"要求先调准琴的原因。**

**问题二：程序确实有一个缺陷 —— 低音弦高八度锁定**

频谱分析给出决定性证据（第 6 弦）：

```
基频区 70–90Hz   ：峰值 76.2 Hz   幅度 34
二次谐波 145–170Hz：峰值 155.3 Hz  幅度 626     ← 基频只有它的 1/18
```

内置麦克风对 60–150Hz 响应很差，把基频压到二次谐波的 1/18，YIN 的"首个低于阈值
的谷"规则于是锁到了高八度，报告 `D#3 / 155.5Hz` 而不是 `D#2 / 78Hz`。

而原来的谐波校验**刻意跳过了 200Hz 以下的全部候选**（那是为了避免第一版激进规则
在短窗口下误伤正确基频），结果就是：**低频区的高八度锁定完全没人管**。
这是技术方案风险表里承诺要缓解、却实际没有兑现的一项，只有真实录音能发现。

### 5.2 修复

在 `harmonic_correct` 中把两类方向相反的误判分开处理：

| 频段 | 误判方向 | 判据 |
|---|---|---|
| 低频区（≤420Hz） | 高八度锁定 | f0/2 仍在吉他音域内（≥60Hz）、且频谱中 f0/2 处**存在**局部峰（幅度 > f0 的 2%，且 > 60–1200Hz 频带中位幅度的 3 倍）→ 向下修正一个八度 |
| 高频区（>420Hz） | 把二次谐波当基频 | 保持原有的**保守**规则：要求 f0 与 f0/2 至少相隔 4 个频点，且 f0/2 处谱峰强于 f0 的 1.2 倍 |

另外把谐波校验用的 FFT 长度改为窗口的 4 倍补零，谱峰定位精度大幅提高。

修复后同一段录音：

```
修复前：D#3 155.5Hz    修复后：D#2 78.10Hz   ✅
```

### 5.3 固件与回归测试

把这段真实录音切段后作为**回归固件**纳入仓库：
`tests/fixtures/real_open_strings.wav`（6 段 × 0.5s，338 KB）。

`tests/test_real_recording.py` 的断言是"每根弦必须落在正确音区（±1.5 个半音）"——
八度误判会偏离约 12 个半音，必然失败。另有单元测试直接验证弱基频场景的向下修正，
以及"没有低八度成分时不得乱改"。

> 测试编写过程中的一个教训：最初按"段首 + 0.15s 固定偏移"取样，第 3、1 弦总是
> 检测不到——因为这两次拨弦只维持了 0.10–0.11 秒就衰减到门限以下，固定偏移正好
> 错过。改为"在段内扫描能量最强的窗口"后通过，这也正是真实程序的做法。

## 6. 供用户实机验证的步骤

```powershell
# 方式一：直接启动程序
dist\JitaTrainer\JitaTrainer.exe

# 方式二：只想验证识别准确度
python tools\capture_fixture.py --list                                  # 找麦克风序号
python tools\capture_fixture.py --device 22 --seconds 20 --segments --lead-in 5
```

**验证前请先把琴调准**（用调音器页或手机 App 都行）。预期：六根弦依次被正确识别，
第 6 弦显示 E2 而不是 E3。

**关于设备**：本机默认设备是蓝牙耳机麦克风（实测静音），唯一在收音的是
`[22] Realtek 麦克风阵列`。需求确定使用**外接 USB 麦克风**，但当前未检测到任何 USB
音频设备。内置阵列的低频响应正是上面这个缺陷的成因，换 USB 麦克风会显著改善，
但仍建议保留这层修正（它对所有低频响应差的设备都有用）。
