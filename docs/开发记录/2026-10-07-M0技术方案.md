## 2. 三个被实测推翻的初始设想

这一节是本轮最有价值的部分——如果不做原型，这三个问题会在 M2 甚至 M5 才爆炸。

### 2.1 「1024 窗口就够了」——错的，物理上不可能

YIN 能测到的最低频率受限于 `tau_max = min(窗口/2, 采样率/fmin)`。测 E2（82.41Hz，周期 582.5 帧 @48kHz）需要窗口 ≥ 1165 帧；按 fmin=70Hz 的设计下限则需要 ≥ 1371 帧。

实测 1024 窗口下 E2 被检测成 **39.29Hz（−1282 音分）**——完全是垃圾值。

**幸运的安全网**：这个错误解的置信度只有 0.597，低于我们设的 0.80 门限，所以它会被**拒绝**而不是变成误判。

### 2.2 「谐波校验越多越保险」——错的，反而制造错误

第一版规则写的是"若 f0/2 频带能量 > f0 的 50%，就判定为八度误判并降八度"。结果在 63 个样本里**误伤 14 次**：把 E2、A2、D3 原本正确的基频又降了一个八度。

根因：短窗口下 FFT 分辨率不足。2048 点 @48kHz 时 bin = 23.4Hz，而 E2 的 f0/2（41.2Hz）与 f0（82.4Hz）只相隔 1.76 个 bin——基频主瓣的泄漏被当成了"存在低八度成分"。

修正为三重保险的保守规则（f0<200Hz 跳过 / 间隔<4 bin 跳过 / 要求局部谱峰且高 1.2 倍），**修正后触发 0 次、误伤 0 次**。

关键认知：因为判定只认音名，**八度误判根本不影响判定对错**，只影响实时音高显示的观感。所以这里"宁可不修，不可修错"是正确取向。

### 2.3 「连续 30 帧都合格才算稳定」——错的，噪声下一帧抖动就全灭

按需求 FR-533"稳定时长 300ms"的字面实现，要求连续 30 帧（10ms 帧移）每帧都合格。实测：**20dB 噪声下 7 个音全部判定失败（0/7）**，而单帧识别明明是 7/7。

改成滑动窗口 + 多数表决（最近 30 帧中某音名占比 ≥70%）后：**20dB 下 7/7**。

## 3. 最终参数（全部由实测选定）

| 参数 | 值 | 依据 |
|---|---|---|
| 分析窗口 | 2048 帧（43ms @48kHz） | 满足 ≥1371 硬约束的最小档；比 4096 快 43ms，抗噪差距由投票补足 |
| 帧移 | 480 帧（10ms） | 判定分辨率 100Hz |
| fmin / fmax | 70Hz / 1400Hz | 低于 E2 留余量；高于 22 品 D6(1174.66Hz) |
| YIN 阈值 | 0.12 | 标准取值，实测无漏检 |
| 置信度下限 | 0.80 | 拦掉 1024 窗口下 E2 的错误解（0.597） |
| 判定机制 | 滑动窗口多数表决，≥70% 一致 | 连续帧方案实测全灭 |
| 稳定时长 | 建议默认 200ms（原定 300ms） | 延迟 282.7ms，满足 ≤300ms；见 CR-001 |

**端到端延迟实测**：窗口 2048 + 稳定 200ms → **282.7ms**。
**误判实测**：16 组配置 × 7 个音 = 112 个样本，**判错 0 次**，噪声下的失败全部是"不敢判"。
**CPU 实测**：单帧 0.5–0.7ms，占 10ms 帧预算的 5–7%。

## 5. 提出的需求变更 CR-001

需求文档内部存在一处**不可同时满足**的冲突：

- FR-533：稳定时长默认 300ms
- NFR §4.3：端到端延迟 ≤300ms

而 `延迟 = 50ms + 窗口 43ms + 稳定时长`，所以 300ms 稳定时长 → 393ms，超标 93ms。

**建议**：稳定时长默认改为 200ms（滑块范围 150–600ms 不变，用户可自行调大）。需用户确认后升需求文档至 v1.1。
