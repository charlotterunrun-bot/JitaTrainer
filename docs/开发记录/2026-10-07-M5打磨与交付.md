## 1. 本轮抓出的三个真 bug

这三个都属于"只有真的去用才会暴露"的类型，而且前两个**足以让程序完全不可用**。

### 1.1 音频线程根本构造不出来（阻断级）

`AnalyzerThread` 是 `@dataclass` 修饰的 `threading.Thread` 子类。dataclass 默认生成
`__eq__`，进而把 `__hash__` 置为 `None`；而 `threading.Thread` 会把自己放进一个
`WeakSet`：

```
TypeError: unhashable type: 'AnalyzerThread'
```

`AudioSession.start()` 正是构造它的地方——**插上麦克风一启动就崩**。

测试没抓到，是因为原有测试都直接用 `FrameAnalyzer`（真正做检测的那个类），
从不构造后台线程；而自检默认不开音频流。**这是一个"用户一用就崩、测试全绿"的缺陷。**

### 1.2 数据类字段遮蔽了 Thread 的内部方法

修好构造之后又发现：dataclass 字段名 `_stop` **遮蔽了 `threading.Thread` 内部的
`_stop()` 方法**（`join()` 在清理时会调用它）：

```
TypeError: 'Event' object is not callable
```

于是"停止"也崩。改名为 `_stop_event`。

### 1.3 备份在 WAL 模式下会丢数据

原实现用 `shutil.copy2` 拷贝数据库文件。但数据库开着 WAL，**未 checkpoint 的事务
还在 `.db-wal` 文件里**——而"刚练完就自动备份"恰恰是最需要保住这些数据的时刻。

改为 SQLite 的**在线备份 API**（`Connection.backup()`），产出一致快照且可与写入并发。
新增回归测试：写入数据后**刻意不 checkpoint**，断言备份里能查到该条记录。

### 2.2 档案导入导出（需求 FR-105）

- 导出为单个 JSON：档案信息、档案设置、训练项、会话、答题明细
- **显式列出字段**（不用 `SELECT *`），格式稳定，以后加字段不会无意改变文件格式
- 会话与答题用 `session_index` 关联，导入时重新分配 id，可导入到任意档案
- 导入两种模式：**新建档案**（重名自动加后缀）或**覆盖当前档案**
- 版本校验：格式不对、版本高于本程序都给出明确错误
- **整体事务**：任何一步失败全部回滚，绝不留半个档案
- 缺失字段用默认值补齐（容忍手改过的文件），必要字段缺失则明确报错

### 2.3 性能测量（对照 §4.3 / §10-16 / NFR-06）

`tools/bench.py` 实测（本机）：

| 指标 | 实测 | 要求 |
|---|---|---|
| 关键模块导入耗时 | ~145 ms | 冷启动 < 3 s |
| 音高检测单帧耗时 | 均值 0.88 ms、P95 0.64 ms | 实时预算 42.7 ms/帧（**占用 2.1%**） |
| 常驻内存峰值 | 65.8 MB | < 300 MB |
| Python 层内存增长 | **+4.7 KB / 909 题** | 不得持续增长 |
| 存活对象数增长 | +253 | 不得持续增长 |

**关于内存测量的一处诚实说明**：压缩模拟（把 2 小时压缩到 1.6 秒跑）会在极短时间内
造出上百万个短命事件对象，常驻内存因此增长约 9~16%，**但这来自分配器碎片而非泄漏**。
用 `tracemalloc` 复核：20 万帧（约 1090 题）后所有分配点合计只增长 **5.4 KB**，
存活对象只多 261 个。因此验收判据以 `tracemalloc` + 存活对象数为准，
RSS 作为参考并注明其局限。

顺带修掉一个真实的无界累加：`SessionStats.reaction_times` 曾是每次答对都 append 的
列表，改为"累加 + 计数"（平均值算法不变），并加了内存回归测试。

### 2.6 自检新增"音频分析线程冒烟"

打包自检里原有的是**采集探测**（`probe_input`），它只走采集层，**不构造
`AnalyzerThread`**——所以 1.1、1.2 那两个致命缺陷它一个都抓不到。

现在自检里多了一项：构造环形缓冲 + 分析线程，灌入合成的 196 Hz 波形，
断言能检测出 196 Hz、线程能干净退出。失败时退出码为 8，构建脚本直接报错。
这样"插上麦克风就崩"这类缺陷以后会在**打包产物**上就被拦住。
