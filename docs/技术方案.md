## 0. 本方案要定的事

M0 不写业务代码，只把**会返工的东西一次性定死**：

1. 音高检测算法与**全部参数**（窗口、帧移、阈值、置信度、投票规则）——已用合成吉他音实测确定；
2. 端到端延迟预算与需求目标之间的冲突及处置（→ 变更请求 CR-001）；
3. 线程模型与数据流（音频线程 / 判定 / UI 如何解耦且不卡顿）；
4. 练习模块插件接口的**函数签名**（决定未来加模块的成本）；
5. 数据表 DDL 与迁移机制；
6. 打包方案与体积预算、验证步骤；
7. 测试策略（哪些必须自动化、用什么音频回归）。

## 3. 架构设计

### 3.1 分层与职责

```
┌──────────────────────────────────────────────────────────────┐
│ UI 层 (PySide6, 主线程)                                       │
│  首页 / 会话设置 / 练习屏 / 小结 / 统计 / 设置 / 调音器 / 向导   │
│  只做渲染与交互；通过 Qt 信号接收音频与判定事件，不直接读音频     │
├──────────────────────────────────────────────────────────────┤
│ 练习模块层 (practice/)                                        │
│  PracticeModule 接口 + 注册表 + 模块一 pitch_find              │
├──────────────────────────────────────────────────────────────┤
│ 调度层 (scheduling/)                                          │
│  Scheduler（配额配比 + 错题回炉）/ SRS（SM-2 间隔）/ 难度建议     │
├──────────────────────────────────────────────────────────────┤
│ 领域层 (core/theory, core/judge)                              │
│  notes / tuning / fretboard / levels / judge 状态机            │
├──────────────────────────────────────────────────────────────┤
│ 音频层 (core/audio)                                           │
│  采集线程 → 环形缓冲 → 门限 → 起音检测 → YIN → 谐波校验 →       │
│  输出 PitchEvent（线程安全队列/信号）                           │
├──────────────────────────────────────────────────────────────┤
│ 数据层 (data/)                                                │
│  SQLite(WAL) + 迁移 + 备份 + 导入导出                          │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向**：UI → 模块 → 调度 → 领域 → 数据；音频层只被"模块/UI"订阅，不反向依赖 UI。领域层与数据层**不依赖 PySide6**（保证可单测、可无头运行）。

### 3.2 线程模型

| 线程 | 职责 | 约束 |
|---|---|---|
| 主线程 (Qt) | 全部 UI 渲染与交互 | 禁止阻塞操作；禁止直接读音频缓冲 |
| 音频采集线程 | `sounddevice.InputStream` 回调 | **回调内只做拷贝入环形缓冲**，绝不做 YIN（回调必须微秒级返回，否则丢帧） |
| 分析线程 | 每 10ms 从环形缓冲取一帧做 YIN + 校验，产出 `PitchEvent` | 单帧预算 10ms，实测耗时 0.5–0.7ms，余量充足 |
| 判定/业务线程（可并入分析线程） | 判定状态机、调度、写库（批量） | 数据库写入批量提交（每 20 条或每 2 秒） |

**跨线程通信**：
- 音频线程 → 分析线程：环形缓冲（`numpy` 数组 + 原子写指针）。
- 分析/判定 → UI：Qt 信号（`Signal(object)`），或 `queue.Queue` + 定时器轮询。**统一用信号**，避免 UI 轮询开销。

**停止顺序**：请求停止 → 关流 → 等分析线程结束 → 冲刷写库。防止退出时丢数据。

## 4. 领域模型设计

### 4.1 基础换算（core/theory/notes.py）

```python
A4_HZ = 440.0
A4_MIDI = 69
NOTE_NAMES = ["C","C#","D","D#","E","F","F#","G","G#","A","A#","B"]

def midi_to_hz(midi: float) -> float          # 440 * 2**((midi-69)/12)
def hz_to_midi(hz: float) -> float
def pitch_class(midi: int) -> int             # midi % 12
def pitch_class_of_hz(hz: float) -> int       # round(hz_to_midi(hz)) % 12
def cents_between(hz_a, hz_b) -> float        # 1200 * log2(a/b)
def nearest_cents_offset(hz: float, pc: int) -> float  # 与指定音名最近同名音的偏差音分
```

> `nearest_cents_offset` 是容差判定的关键：判定只认音名，所以"偏差音分"要按**同名音**计算（例如弹 82.9Hz 时，与 E2=82.41 比是 +10 音分，而不是与 E1/E3 比）。

## 5. 音频层设计

### 5.1 设备与采样

- `sounddevice.query_devices()` 列举输入设备；默认设备标 `default`。
- 采样率优先 48000；失败则回退设备默认采样率，**算法按实际采样率自适应**（所有参数以秒/频率表达，不写死采样点）。
- 声道：单声道（多声道设备取第 1 声道）。
- 数据类型：`float32`。
- 块大小：480 帧（10ms）——与帧移一致，延迟最低。

### 5.2 环形缓冲（ring.py）

- 容量：≥ 8192 帧（约 170ms），保证分析线程落后时也不丢窗。
- 单生产者（音频回调）单消费者（分析线程）。
- 溢出策略：覆盖最旧数据并计数（计入诊断日志），不阻塞回调。

### 5.3 起音门限与噪声地板

首次运行向导测量 3 秒静默，得到噪声地板 `noise_floor_db`，建议门限：

```
gate_db = noise_floor_db + 12 dB          （用户可调 ±）
frame_rms_db < gate_db  →  该帧标记为静音，不进入判定
```

同时用**起音（attack）检测**辅助定位拨弦时刻：帧 RMS 相对前 3 帧均值上升 ≥ 8 dB 视为起音。起音时刻用于：
- 反应时间的计时起点参考（FR-541 的辅助口径）；
- 宽容期结束后，从第一个起音开始参与稳定判定（避免把衰减尾巴当成新弹奏）。

### 5.4 YIN 实现（pitch_yin.py）

参数（**实测确定**，见 §6）：

| 参数 | 值 | 依据 |
|---|---|---|
| 分析窗口 | 2048 帧（43ms @48kHz） | §6.6 矩阵：延迟与抗噪的最优折中 |
| 帧移 | 480 帧（10ms） | 判定分辨率 100Hz，足够支撑 150ms 级稳定时长 |
| `fmin` | 70 Hz | 低于 E2(82.41) 留余量；约束窗口 ≥ 2·sr/fmin = 1370 |
| `fmax` | 1400 Hz | 高于 22 品 D6(1174.66) |
| YIN 绝对阈值 | 0.12 | 标准取值，实测无漏检 |
| 置信度下限 | 0.80 | 拦掉 1024 窗口下 E2 的错误解（其置信度仅 0.597） |

算法步骤：
1. 差分函数 `d(τ)`，用 FFT 互相关计算（避免 O(N²)）；
2. 累积均值归一化 `d'(τ)`；
3. 绝对阈值法取**第一个**低于 0.12 且为局部极小的 τ（首峰规则天然抑制"取到 2 倍周期"的八度升高错误）；
4. 抛物线插值细化 τ → 频率；
5. 置信度 = `1 - d'(τ*)`，低于 0.80 直接判为无有效音高。

> 代码骨架已在 [tools/pitch_bench.py](../tools/pitch_bench.py) 中验证，M1 直接迁移为 `pitch_yin.py` 并补单元测试。

### 5.5 谐波校验（保守策略）

**教训**：第一版规则是"若 f0/2 频带能量 > f0 的 50% 就降八度"，结果在 63 个样本里误伤 14 次——短窗口下 FFT 分辨率不足（2048 点 @48kHz 时 bin=23.4Hz，E2 的 f0/2 与 f0 仅隔 1.76 个 bin），把基频主瓣泄漏当成了低八度成分，**把正确的音改错**。

**修正后的规则**（三重保险，满足任一即跳过校验）：

1. `f0 < 200 Hz` → 跳过（低频区分辨率不足，直接信任 YIN）；
2. `f0/2` 与 `f0` 的间隔 < 4 个频点 → 跳过；
3. 要求 `f0/2` 处存在**局部谱峰**（而非频带最大值），且其幅度 > 1.2 × `f0` 处谱峰。

实测：修正后 **触发 0 次、误伤 0 次**。

> 重要认知：因为判定只认音名，**八度误判不影响判定对错**，只影响实时音高显示的观感与调音器。所以此处"宁可不修，不可修错"是正确的取向。

### 5.6 输出事件

## 6. 实测数据（本方案的全部量化依据）

> 测试条件：分析窗口取自合成吉他音的稳定段（起音后 150ms），合成方式为 12 次谐波、幅度 ∝ 1/n^1.2、指数衰减、可选白噪声；采样率 48kHz。
> 噪声定义：**白噪声标准差相对信号峰值的比值**；20dB = 0.1，15dB ≈ 0.18，10dB = 0.32。
> 复现命令见 §19。

### 6.1 分析窗口下限约束（硬约束）

`tau_max = min(window//2, sr/fmin)`，必须覆盖 E2 的周期 582 帧：

| 窗口 | tau_max | E2（周期 582）是否可表示 |
|---|---|---|
| 1024 | 512 | **否 —— YIN 无解** |
| 2048 | 685 | 是 |
| 4096 | 685 | 是 |

**结论：窗口必须覆盖周期。** 两个口径都要满足：
- 测 E2 本身需要 ≥ 2×582.5 = **1165 帧**；
- 按设计下限 `fmin = 70Hz` 需要 ≥ 2×48000/70 = **1371 帧**（fmin 比 E2 留了余量，是为了容忍琴略低或弦略松）。

→ **窗口 ≥ 1371 帧**，故 1024 方案直接淘汰，2048 是满足约束的最小档位。

### 6.2 单帧识别精度（无噪声，未做谐波校验）

| 音 | 真值(Hz) | 1024 窗口 | 2048 窗口 | 4096 窗口 |
|---|---|---|---|---|
| 6弦空弦 E2 | 82.41 | **39.29 (−1282 音分)** | 82.40 (−0.1) | 82.41 (−0.0) |
| 5弦空弦 A2 | 110.00 | 109.98 (−0.3) | 110.00 (−0.0) | 110.00 (+0.0) |
| 4弦空弦 D3 | 146.83 | 146.86 (+0.4) | 146.84 (+0.1) | 146.84 (+0.1) |
| 3弦空弦 G3 | 196.00 | 196.00 (+0.0) | 196.01 (+0.1) | 196.00 (+0.0) |
| 2弦空弦 B3 | 246.94 | 246.96 (+0.1) | 246.95 (+0.0) | 246.95 (+0.0) |
| 1弦空弦 E4 | 329.63 | 329.65 (+0.1) | 329.63 (−0.0) | 329.63 (+0.0) |
| 1弦12品 E5 | 659.26 | 659.31 (+0.2) | 659.30 (+0.1) | 659.30 (+0.1) |

**YIN 精度极好（≤0.4 音分），唯一失败点是 1024 窗口下的 E2 —— 且其置信度仅 0.597，会被 0.80 的置信度门限拦下，不会变成误判。**

### 6.3 单帧抗噪（判对标准 |音分| ≤ 25）

| 窗口 | 无噪声 | 20dB | 10dB |
|---|---|---|---|
| 1024 | 6/7 | 3/7 | 4/7 |
| 2048 | 7/7 | 4/7 | 3/7 |
| 4096 | 7/7 | 7/7 | 4/7 |

**单帧方案在噪声下不可靠 → 必须引入多帧判定（§6.7）。**

### 6.4 单帧耗时

| 窗口 | 单帧耗时 |

| 1024 | 0.5 ms |
| 2048 | 0.5 ms |

| 4096 | 250 ms | 7/7 | 7/7 | 0/7 | 375.3 ms |
| 4096 | 300 ms | 7/7 | 7/7 | 0/7 | 425.3 ms |

**选型结论**：窗口 2048 + 稳定时长默认 200ms → **延迟 282.7ms，满足 NFR ≤300ms**，且 0dB/20dB 全对。
（4096 的抗噪优势在引入多帧投票后不再必要，反而拖慢 43ms。）

### 6.7 判定机制对比：连续帧 vs 滑动窗口投票

| 机制 | 20dB 判定 |
|---|---|
| 连续 30 帧每帧都须合格（严格） | **0/7（全灭）** —— 一帧置信度抖动就重置计数 |
| 滑动窗口 30 帧 + 多数表决（≥70% 一致） | **7/7** |

**结论：判定必须用滑动窗口多数表决，不能要求连续帧全合格。** 这是需求 FR-533"稳定时长"的正确实现方式。

### 6.8 误判分析（"不可冤判"的硬证据）

| 窗口 | 稳定时长 | 噪声 | 正确 | **判错（冤判）** | 未判定（不敢判） |
|---|---|---|---|---|---|
| 2048 | 150 ms | 无噪声 | 7/7 | **0** | 0 |
| 2048 | 150 ms | 20dB | 7/7 | **0** | 0 |
| 2048 | 150 ms | 15dB | 6/7 | **0** | 1 |
| 2048 | 150 ms | 10dB | 0/7 | **0** | 7 |
| 2048 | 300 ms | 20dB | 7/7 | **0** | 0 |
| 2048 | 300 ms | 15dB | 0/7 | **0** | 7 |
| 4096 | 150/300 ms | 10–20dB | — | **0** | 全部为未判定 |

**合计 112 个样本，判错 0 次。** 噪声下的失败一律是"拒绝判定"，符合需求「宁可慢一点，不可冤判」。M1 须把这条固化为自动化回归测试。

### 6.9 谐波校验的误伤（反面教材，已修）

## 7. 判定引擎状态机（core/judge）

```
                    ┌──────────┐
     出题渲染完成 → │ 宽容期    │  时长 = settings.rehearsal_grace（默认 2.0s）
                    │ GRACE    │  PitchEvent 仅用于实时音高显示，不计入判定
                    └────┬─────┘
                         │ 超时 或 检测到起音
                         ▼
                    ┌──────────┐
                    │ 稳定检测  │  滑动窗口 N = 稳定时长/帧移（默认 200ms → 20 帧）
                    │ STABLE   │  每帧：conf ≥ 0.80 才计入有效帧
                    │          │  有效帧中众数占比 ≥ 70% 且有效帧 ≥ 40%·N → 判定
                    └────┬─────┘
              未达共识   │   达到共识
                 ┌───────┴────────┐
                 ▼                ▼
        ┌──────────────┐   ┌──────────────┐
        │ 无音高/不稳定 │   │ 判定结果      │
        │ 继续等待      │   │ 与目标音名比对 │
        │ 达超时(8s) →  │   └───┬──────┬───┘
        │ 记"未作答"    │       │      │
        └──────────────┘    正确│      │错误
                              ▼      ▼
                      ┌─────────┐ ┌─────────────┐
                      │ 反馈成功 │ │ 反馈错误并停留 │
                      │ 出下一题 │ │ 记录本次尝试   │
                      └─────────┘ │ 重置稳定窗口   │
                                  └─────────────┘
```

模式差异（对应需求 FR-535）：

| 模式 | GRACE 行为 | STABLE 起点 |
|---|---|---|
| 宽容期模式（默认） | 宽容期内不判定 | 宽容期结束后 |
| 严格模式 | 宽容期 = 0 | 出题瞬间 |
| 宽容模式（不判错） | 不判定对错 | 只累计"弹对所用时长"，任何错误只记录不反馈 |

其它判定规则：
- **判定比较的是音名**（`pitch_class`），与八度/弦/品无关；
- 容差判定：`|cents| ≤ tolerance_cents`（默认 25，滑块 10–50）；
- 错误后重置稳定窗口，允许无限次重试（需求 §14-4）；
- 超时（默认 8s）记"未作答"，计入薄弱项但不计入答错次数（区分统计口径）。

## 8. 练习模块插件接口（practice/base.py）

```python
class PracticeModule(Protocol):
    id: str                                  # "pitch_find"
    name: dict[str, str]                     # {"zh_CN": "看谱找音", "en_US": "Note Finding"}
    icon: str
    version: str

    def default_config(self) -> dict: ...
    def settings_schema(self) -> list[SettingField]: ...      # 自动渲染设置面板
    def prepare(self, profile: Profile, config: dict) -> None: ...
    def generate(self, ctx: QuestionContext) -> Question: ...  # 由调度层驱动
    def render_spec(self, q: Question) -> RenderSpec: ...      # 声明怎么画（TAB/未来和弦图）
    def judge(self, q: Question, ev: PitchEvent, state: JudgeState) -> JudgeOutcome: ...
    def stats_fields(self) -> list[StatsField]: ...            # 本模块特有统计维度
    def on_session_end(self, summary: SessionSummary) -> None: ...
```

关键约束（保证"可扩展"不是口号）：

1. **判定策略可替换**：`judge` 是模块自己的实现，因此未来「音名+八度」「指定弦位」只需新增策略类，不改动音频层与调度层；
2. **渲染与逻辑分离**：模块只产出 `RenderSpec`（数据），由 UI 的通用控件负责绘制 → 未来加五线谱/和弦图是加控件，不是改模块；
3. **调度不感知模块细节**：`QuestionContext` 只包含"本次该出哪些训练项"，模块负责把训练项变成具体题目；
4. 注册方式一行：

```python
@register_module
class PitchFindModule: ...
```

M1/M2 交付时必须附一个**示例空模块**（`practice/_example/`）作为扩展文档的可执行范例。

## 9. 调度与记忆曲线

### 9.1 训练项

`item_key = f"note={NOTE_NAMES[pc]}|level={level_id}"`（例：`note=B|level=L2`）

### 9.2 SRS 参数（简化 SM-2）

```python
INTERVALS_DAYS = [0, 1, 3, 7, 16, 35, 75, 160]   # 索引 0 表示当天回炉

答对（首次稳定音即正确）: idx = min(idx+1, len-1); due_at = now + INTERVALS_DAYS[idx]
答错（含重试后答对）    : idx = 0;                 due_at = now + 0 天（当天回炉）; lapses += 1
跳过/超时              : idx = 0;                 due_at = now + 0 天;            lapses += 0.5
带提示答对              : 不改变 idx，仅记录
```

### 9.3 出题调度（每 10 题一个配额窗口）

| 优先级 | 来源 | 配额 | 选择方式 |
|---|---|---|---|
| 1 | 到期复习（`due_at ≤ now`） | ≤4 | 逾期越久越优先 |
| 2 | 薄弱项（未到期但错误率高/反应慢） | ≤3 | 加权随机 |
| 3 | 新题 | ≥3 | 熟练度最低优先 |

薄弱项权重：

```
w = (1 + 2.0 × error_rate)
  × (1 + 1.5 × max(0, (target_rt − avg_rt) / target_rt))     # target_rt = 2500ms
  × (0.5 + 0.5 × min(1, 距上次练习天数 / 7))
```

**错题回炉**：本次答错/跳过/超时的题，隔 5–8 题（随机）重现；连续 2 次答对移出；回炉不占配额但总量 ≤ 会话题量的 30%。

**可复现**：调度器接受随机种子，给定种子与历史可确定性重放（用于测试与问题复现）。

## 16. 需求变更请求 CR-001

**背景**：需求文档 FR-533 规定"稳定时长默认 300ms"，NFR §4.3 规定"端到端延迟 ≤300ms"。实测表明两者**不可同时满足**：

```
延迟 = 50ms + 窗口(43ms) + 稳定时长(300ms) = 393ms  >  300ms
```

**建议变更**：

| 项 | 原值 | 建议值 | 理由 |
|---|---|---|---|
| 稳定时长默认值 | 300 ms | **200 ms** | 实测 282.7ms 满足 ≤300ms；0dB/20dB 下判定 7/7；滑块范围 150–600ms 不变，用户仍可自行加大 |
| 窗口 | 未规定 | **2048 帧（43ms）** | 满足 ≥1370 的硬约束；投票机制下抗噪已足够 |

**影响**：判定更快、更符合"即时反馈"的产品直觉；抗噪能力由"滑动窗口投票"提供，而非拉长稳定时长。
**风险**：真实环境若噪声较大，用户可自行把稳定时长调回 300ms 以上（设置项已存在）。

> 需要用户确认后，需求文档升为 v1.1 并同步 GitHub。
